# 驾校科目一智能助教｜技术适配声明 V0.1

> 状态：开发前技术评审稿  
> 日期：2026-08-26  
> 输入依据：当前项目PRD与已确认项目文档、《AI Agent 产品 Vibe Coding 通用技术栈手册 V2.1》  
> 本文只完成技术适配，不代表已经开始开发。

## 1. 产品形态判断

本项目是面向真实驾校学员的B2B2C科目一AI答疑产品。驾校负责交付，学员首版通过自建Web使用。

核心任务是：学员提出科目一问题，系统通过标准题库、RAG和模型提供正确、易懂、带依据的回答；不能可靠回答时进入“不懂就问校长”。

它不是自由规划型Agent。第一阶段采用：

- 固定业务流程；
- 后端代码状态机；
- Dify负责编排Prompt、RAG和模型调用；
- 标准答案、权限、状态和风险决策由确定性代码控制；
- 不引入多Agent，不允许模型自主执行高风险动作。

## 2. 开发路径

选择：**最小纵向切片**。

原因：回答是否易懂、依据是否清晰、二次解释是否有效以及转人工是否顺畅，必须通过最小真实Web界面一起验证。第一阶段只打通一条链路，不开发整套MVP页面。

```text
邀请码进入
→ 文字提问
→ 标准题/RAG路由
→ 有依据的结构化回答
→ 已解决/还不懂/答案有问题
→ 第二种解释或创建校长工单
→ 数据和状态可恢复
```

## 3. 采用的默认方案

| 领域 | 采用方案 | 原因 |
|---|---|---|
| 总体架构 | 模块化单体 | 适合MVP和30–50人试点，避免微服务复杂度 |
| 后端 | Python 3.11.x＋FastAPI | 适合AI/RAG和可测试API |
| 数据校验 | Pydantic | 校验API和模型结构化输出 |
| 后端测试 | pytest | 覆盖状态、解析器和错误路径 |
| Web | Next.js＋TypeScript＋App Router | 支持Web首发和响应式交互 |
| 样式 | Tailwind CSS＋项目设计Token | 落实已确认Loom视觉基线 |
| 前端检查 | ESLint＋TypeScript | 保证类型和基础质量 |
| API | `/api/v1` | 便于未来小程序及ERP接入 |
| ORM/迁移 | SQLAlchemy＋Alembic | 数据关系明确且需要可迁移 |
| 本地数据库 | SQLite | 第一阶段低并发验证成本最低 |
| AI编排 | Dify | 项目已确定，用于Workflow和RAG |
| 代码管理 | Git | 版本留痕、恢复和协作 |

## 4. 触发的按需模块

| 模块 | 触发原因 | 第一阶段 |
|---|---|---|
| 标准题库服务 | 标准答案不能由模型决定 | 启用 |
| Dify知识库/RAG | 开放理论问题需要可信依据 | 启用最小知识集 |
| Embedding/Rerank | 需要召回和重排 | 由Dify承载，模型配置化 |
| SSE | 需要展示回答过程并控制首屏时间 | 启用 |
| 审计记录 | 回答和人工处理必须可追踪 | 启用 |
| OCR | PRD包含图片问题 | 第一阶段暂缓 |
| 对象存储 | 图片需要安全存储和清理 | 第一阶段暂缓 |
| PostgreSQL | 真实远程试点和并发写入 | 试点部署前评估 |
| 任务队列 | 批量评测、导入和清理 | 达到实际需求后启用 |

## 5. 必要偏离与边界

### 5.1 不采用完全后端先行

本项目采用最小纵向切片，因为学员问答交互本身决定产品是否可用。这不代表提前开发完整前端。

### 5.2 不另外建设Chroma

项目已经采用Dify。第一阶段优先使用Dify知识库、Embedding和Rerank，避免两套向量索引。若评测无法满足召回、版本过滤、引用追踪或数据隔离，再评估独立向量服务。

### 5.3 第一阶段使用SQLite

通过SQLAlchemy和Alembic隔离数据库实现。进入真实学员试点前重新评估PostgreSQL、备份和并发需求。

### 5.4 Dify不承担业务主状态

Dify承担分类、RAG、Prompt和模型调用。FastAPI承担身份、标准题库、会话、反馈、工单、权限、审计和风险决策。

### 5.5 模型只作为候选配置

PRD中的模型名称需要在开发前核验真实可用ID、地区、价格和限流。模型ID、base_url、超时和参数从后端配置读取，不写死在代码里。

## 6. 建议系统结构

```text
Next.js Web
    ↓ 受控API
FastAPI业务后端
    ├─ 邀请码与匿名学员
    ├─ 会话、问题、回答与反馈
    ├─ 标准题确定性匹配
    ├─ 风险与回答状态机
    ├─ 校长工单状态机
    └─ 审计与指标事件
    ↓
AI适配层
    ├─ Dify Workflow
    ├─ RAG与引用
    ├─ Prompt版本
    └─ 模型调用与错误适配
    ↓
SQLite＋标准题库＋独立评测数据
```

## 7. 强制底线检查

| 项目 | 当前状态 | 开发要求 |
|---|---|---|
| 密钥安全 | 待实施 | Key只由后端读取，不进入前端、仓库和日志 |
| 输入校验 | 待实施 | 邀请码、文本、枚举和ID全部校验 |
| 模型输出校验 | 待实施 | 确定性解析＋Pydantic强校验 |
| 状态可恢复 | 待实施 | 问题、回答、反馈和工单持久化 |
| 标准答案控制 | 已明确 | 模型不得决定或覆盖标准答案 |
| 错误边界 | 待实施 | 统一错误结构，不展示程序堆栈 |
| Prompt管理 | 待实施 | 独立文件、版本可追踪 |
| 高风险动作 | 已限定 | AI不能自动发布知识、改标准答案或关闭争议工单 |
| 双层测试 | 待实施 | mock自动化＋真实模型端到端冒烟 |
| 测试真实性 | 强制 | 无真实Key时必须标记“真实冒烟待验” |

## 8. 数据与隐私

- 第一阶段只处理匿名学员ID、驾校ID、科目、车型/地区、问题和必要上下文；
- 身份证、财务、缴费和完整联系方式不得进入Prompt或RAG；
- 普通日志不保存完整学员问题；
- 正式知识库与评测集隔离；
- 第一阶段没有图片，不启动图片7天删除机制；
- OCR阶段同步加入MIME、大小、安全文件名和定时清理；
- 进入真实试点前完成对话180天、学习记忆试点后30天、删除申请和匿名化机制。

## 9. 双层测试

### mock自动化测试

覆盖邀请码、标准题命中、RAG有/无依据、来源冲突、模型格式错误、超时、反馈、二次解释、工单状态、SSE收尾、越权和重启恢复。

### 真实模型冒烟

至少跑通：

1. 标准题完整链路；
2. 开放理论RAG链路；
3. 无依据拒答或转人工；
4. 二次解释；
5. 真实模型失败路径。

记录模型、Workflow、Prompt版本、首字时间、总耗时、Token、成本、重试和人工质量结论。

## 10. 主要风险

| 风险 | 控制方式 |
|---|---|
| 模型覆盖标准答案 | 标准答案由后端锁定，模型只解释 |
| 相似题误匹配 | 精确匹配优先，阈值不足转RAG或人工 |
| 回答偏离证据 | 引用约束、结构校验和一致性检查 |
| Dify承载过多状态 | 状态和权限保留在业务后端 |
| 流式回答中断 | 必须以`done`或`error`结束，残缺内容不入正式答案 |
| SQLite进入正式并发 | 真实试点前评估迁移PostgreSQL |
| 模型接口变化 | 统一AI适配层和环境配置 |
| UI规则冲突 | 以Loom设计系统为唯一有效基线 |

## 11. 开发前待确认

1. 使用现有Dify环境，还是新建国内云自托管环境；
2. 是否已有可用模型Key；
3. 第一阶段模型测试预算上限；
4. 第一批标准题和知识卡片由谁进行专业审核。

## 12. 当前结论

- 采用最小纵向切片；
- 采用模块化单体，不采用微服务和多Agent；
- 标准题、状态和权限由业务后端控制；
- Dify负责AI编排和RAG；
- 第一阶段暂不开发OCR、完整后台、提醒和看板；
- 当前没有开始开发。
