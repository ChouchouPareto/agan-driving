## 1. 项目背景

现有通用驾考App主要服务学员自主刷题，难以进入驾校真实服务一线，也难以体现驾校、教练与学员之间的服务关系。学员遇到看不懂、反复做错或质疑答案的问题时，仍需要快速、可信、易懂并有人负责的帮助；教练则面临大量重复理论咨询。

项目希望由驾校把AI服务交付给真实学员，以科目一智能答疑作为MVP切口，通过题库、RAG、大模型和真人教练协同，提高学员体验并降低驾校重复服务成本，为口碑、续费和增购提供依据。

## 2. 产品定位

> 一套由驾校交付给学员、以标准题库保证答案、以AI提供通俗解释、以“不懂就问校长”服务处理异常，并能记住学员薄弱点的科目一智能助教。

产品不是：

- 面向所有C端用户的通用刷题App；
- 以招生获客为核心的智能客服；
- 替代ERP、教务、排课和财务的驾校管理系统；
- 只依赖大模型自由回答的聊天机器人。

## 3. 产品目标与价值闭环

### 3.1 学员价值

- 快速获得正确答案；
- 看懂为什么这样选，以及容易错在哪里；
- 系统记住历史问题、错题和薄弱知识点；
- 在关键时机获得有限、相关的学习提醒；
- 对争议答案能够获得AI复核或进入“不懂就问校长”处理。

### 3.2 驾校价值

- AI承接高频重复咨询；
- 教练只处理异常、争议和高价值问题；
- 看到学员使用、问题解决和薄弱知识分布；
- 以学员体验和服务效率支撑口碑、续费与增购判断。

### 3.3 核心闭环

```text
驾校交付服务
→ 学员文字/拍照提问
→ 标准题库或RAG提供可信事实
→ AI生成简短易懂的解释
→ 学员确认是否看懂
→ 系统记录错题和薄弱知识点
→ 关键事件触发有限提醒
→ 异常问题进入“不懂就问校长”兜底
→ 学员感受到进步与被服务
→ 驾校看到效果与效率价值
```

## 4. MVP用户与角色

| 角色 | 主要目标 | MVP职责 |
|---|---|---|
| 科目一学员 | 快速解决题目和理论疑问 | 提问、查看解释、继续追问、反馈是否解决或提出异议 |
| 教练/专业审核员 | 处理异常并维护答案质量 | 查看预警、核对依据、修正答案、回复学员 |
| 驾校负责人/试点运营 | 了解服务效果 | 查看基础效果看板和高频问题 |
| 项目运营/知识管理员 | 维护系统与知识资产 | 导入题库、管理版本、发布审核内容、查看评测日志 |

## 5. MVP范围

### 5.1 P0纳入

1. 自有Web学员端；
2. 邀请码或测试账号进入；
3. 文字输入与截图/拍照识题；
4. 科目一标准题匹配和开放理论问答；
5. 标准答案、通俗解析、易错点与可折叠依据；
6. “我看懂了”“还是不懂”“答案有问题”“再练类似题”等后续动作；
7. 历史问答、错题和薄弱知识点的轻量记忆；
8. 连续同类错误、薄弱点小结和临考复习建议等有限提醒；
9. 机器评测、异常预警和教练审核闭环；
10. 驾校基础效果看板；
11. 题库、法规和教学解析内容的导入、来源、版本与审核管理。

### 5.2 MVP不纳入

1. 完整刷题与模拟考试系统；
2. 复杂个性化学习计划；
3. 高频营销式或全渠道消息推送；
4. 科目二、科目三和科目四的完整服务；
5. 完整ERP、教务、招生CRM、排课、财务和商业计费；
6. 多驾校复杂租户与完整权限体系；
7. 直接接入全部第三方小程序或ERP。

## 6. 学员端核心流程

### 6.1 进入

> 驾校/教练发送邀请 → 学员打开Web端 → 使用邀请码或测试账号进入 → 系统加载最小档案与必要数据说明。

### 6.2 提问

学员可以：

- 输入题干、选项或自然语言问题；
- 上传截图或拍摄题目；
- 对OCR结果进行必要校正；
- 在当前问题下继续追问。

### 6.3 回答结构

默认短答、口语化、像教练解释：

1. 直接答案；
2. 一句话解释；
3. 为什么这样选；
4. 易错提醒；
5. 可折叠的法规或知识依据；
6. 下一步操作按钮。

### 6.4 回答后的分支

```text
我看懂了
→ 完成本次问题并更新掌握状态

还是不懂
→ 换一种更简单的表达、例子或对比继续解释

答案有问题
→ 停止强化原答案 → 机器复核 → 进入“不懂就问校长”状态链路
→ 提交给校长 → 校长在摸鱼 → 校长处理中 → 校长已回复 → 校长说好了

再练类似题
→ 从已审核题库返回同知识点题目
```

## 7. 轻量学习记忆

MVP记录：

- 学员问过的题目与问题；
- 答错、反复询问或提出异议的题目；
- 关联知识点；
- 学员是否确认看懂；
- 近期薄弱知识点及变化；
- 当前科目、车型、地区和必要的规则版本；
- 考试日期等提醒所需信息（由学员提供或确认）。

MVP不记录与学习无关的长期人格信息，也不把完整身份证、财务和缴费信息放入模型上下文。

## 8. 有限主动提醒

已确认提醒类型：

- 连续出现同类错误；
- 形成明显薄弱知识点；
- 生成阶段性薄弱点小结；
- 临近考试时提供针对性复习建议；
- 异常问题提醒教练介入。

已确认规则：

- 7天内同一知识点连续出现2次错误时触发薄弱点提醒；
- 累计形成3个及以上薄弱知识点时生成学习小结；
- 考试前7天、3天和1天提供针对性复习建议；
- MVP仅在Web端内展示提醒，不依赖外部消息推送；
- 普通学习提醒每天最多1条、每周最多3条；
- 学员可以关闭普通学习提醒，但不能关闭答案异议处理结果通知。

## 9. AI处理链路

```text
用户输入
→ OCR/视觉识别（图片场景）
→ 意图分类与问题改写
→ 标准题/开放问题路由
→ 题库确定性匹配或RAG检索
→ 大模型按Prompt生成解释
→ 标准答案、引用、冲突与置信度检查
→ 正常展示或触发异常预警
→ 学员反馈、教练修正、知识与评测沉淀
```

### 9.1 四条核心工程线

1. 题库与规则工程：保证标准答案、地区/车型/版本和更新；
2. RAG工程：清洗、切分、Embedding、混合检索、Rerank和引用；
3. PE工程：问题分类、解释结构、拒答边界、风险提示和Prompt版本；
4. 评测与审核工程：评测集、自动检查、错误归因、真人复核和回归测试。

## 11. 知识资产

### 11.1 标准题库

负责“答案是什么”，采用结构化存储。至少包含题目、选项、答案、解析、图片、知识点、易错点、车型、地区、科目、来源、版本、生效/失效时间和审核状态。

### 11.2 法规知识库

负责“为什么”，至少包含法规名称、发布机构、条款编号、条款原文、通俗解释、适用范围、生效/失效时间、来源链接、关联知识点和审核状态。

### 11.3 教学解析库

负责“怎么讲更容易懂”，至少包含教练解释、记忆方法、常见误区、正反案例、相似概念对比、关联题目和审核版本。

### 11.4 来源路线

供应商资料到位前，由项目方自行整理小规模种子题库用于验证；供应商资料到位后，核验授权、版本、地区/车型范围和完整性，再完成导入、去重、审核和发布。GitHub及公开网络内容只能作为整理线索和测试候选。

首版准备不少于500道高频标准题和50—100个高频知识点解析卡，评测集另行维护，不与生产知识混用。

## 12. 异常预警与教练审核

学员侧统一将异常求助与处理服务命名为“**不懂就问校长**”。该名称是用户可见的品牌化服务入口；后台技术对象仍为异常审核工单，可根据驾校排班分配给校长、值班教练或项目运营。

触发候选条件：

- 未命中可信题库或知识库；
- 多个可信来源结论冲突；
- 题目信息不完整或OCR无法可靠识别；
- 车型、地区或规则版本不明确；
- 学员反馈“答案有问题”；
- 涉及新规、政策更新或安全敏感内容；
- 同类问题连续出现异常。

已确认的服务规则：

- 工作时间内目标响应时间为2小时；
- 非工作时间向学员展示预计处理时间；
- 超时后自动提醒试点运营人员；
- 学员端展示“提交给校长—校长在摸鱼—校长处理中—校长已回复—校长说好了”的趣味处理状态；
- 具体审核责任人、工作时间定义和排班方式在试点准备阶段由供应商与项目方共同确认。
- 试点默认由供应商指定一名值班教练，项目运营作为后备；服务时间为每日9:00—18:00；P0问题由项目负责人和专业审核人共同决定暂停及恢复。

## 13. 驾校基础效果看板

MVP展示方向：

- 本期使用学员数和活跃学员数；
- 提问总量；
- 回答正确率；
- 首次问题解决率；
- AI独立解决率；
- “不懂就问校长”介入量及响应时间；
- 学员满意度；
- 高频问题与薄弱知识点。

已确认权限：

- 驾校负责人查看驾校整体汇总数据；
- 教练只查看自己负责学员的异常问题；
- 项目运营查看完成AI质量评测和故障定位所必需的日志；
- 看板默认不展示学员之间的公开排名；
- 高频问题和薄弱知识点以匿名汇总形式展示；
- 只有进入异常处理时，教练才可查看对应学员的具体问答记录。

更新规则：普通使用、提问和解决数据按日更新；答案异议、P0问题和待审核数量实时更新。各指标计算公式在数据字典中固定。

## 14. 数据、身份与系统边界

### MVP

- 自有Web端；
- 邀请码或测试账号；
- 轻量学员档案；
- 不依赖真实ERP；
- AI服务通过独立API与Web端解耦。
- 邀请码采用一人一码，不强制绑定手机号；
- 系统生成匿名学员ID；
- 更换设备时由运营重新发码恢复原账号；
- 试点结束后停止账号使用，并按已确认规则处理个人学习数据。

### 长期

- ERP/SaaS继续作为学员身份、当前科目、教练关系和考试安排的事实源；
- AI系统只读取完成服务必要的上下文；
- 通过API、Webhook、SSO和H5/WebView嵌入；
- AI系统不重建完整ERP，也不直接修改第三方数据库。

## 15. 指标与验收方向

### 15.1 MVP核心质量门槛

回答正确率，包括：

- 标准答案正确；
- 解释不与答案或依据冲突；
- 引用与问题相关；
- 无法确定时不编造；
- 回答针对学员实际问题。

已确认的量化门槛：

| 指标 | MVP门槛 |
|---|---:|
| 已精确命中题库后的标准答案正确率 | 100% |
| 标准题全链路正确率（含识别、匹配和回答） | ≥98% |
| 开放理论问答人工评审正确率 | ≥90% |
| 回答与引用依据一致率 | ≥95% |
| 拍照题干及选项完整识别率 | ≥95% |
| 无依据时正确拒答或进入“不懂就问校长”的比例 | ≥95% |

### 15.2 学员体验

- 首次问题解决率；
- 学员满意度；
- 重复使用率；
- “还是不懂”后的二次解决率；
- 薄弱知识点改善情况。

试点目标：

- 首次问题解决率≥80%；
- 学员满意度≥4.2/5；
- 二次解释后的问题解决率≥70%；
- 普通文字提问首屏响应尽量控制在5秒以内；
- 学员提出的答案异议100%进入可追踪状态。

### 15.3 服务与商业验证

- AI独立解决率；
- “不懂就问校长”介入率及响应时间；
- 教练重复咨询量变化；
- 试点驾校续费或增购意愿；
- 学员推荐或好评意愿。

### 15.4 试点规模与统计方式

- 首轮邀请30—50名真实科目一学员；
- 连续运行4周；
- 标准题通道和开放问答通道分别统计正确率，不混为一个指标；
- 标准题通道设置高于开放问答的上线门槛；
- 本PRD第15.1节的门槛作为首轮上线标准；基线测试只能用于调优实现，不能绕过P0为0和标准答案正确性要求。

## 15.5 商业验证

- 第一轮与明确的驾校供应商开展联合免费试点；
- 试点开始前约定中期和结束效果评审节点；
- 结束评审除使用数据外，必须收集供应商的付费、续用或扩大学员范围意愿；
- 下一阶段是否付费或扩大范围，根据质量、体验、服务效率和供应商采购反馈共同判断。

## 16. 非功能与安全要求

- 每次回答可追踪题库版本、知识来源、模型和Prompt版本；
- 供应商、驾校和学员数据遵循最小必要原则；
- 未审核知识不进入确定性标准答案通道；
- 图片上传、日志和学员记忆需要明确保存期限与删除机制；
- 模型、OCR和RAG失败时提供明确状态，以及重试或“不懂就问校长”路径；
- 核心回答链路需记录耗时和调用成本。

### 16.1 异常等级

#### P0：阻断上线或需要暂停对应链路

- 标准题返回错误答案且没有风险提示；
- 使用过期法规造成错误结论；
- 不同学员之间发生个人数据泄露；
- 学员提出答案异议后，系统继续强化未经复核的原答案；
- 已审核下线的错误内容再次上线。

发现P0后，暂停对应题目、知识或回答链路，修复并完成回归测试后恢复。

#### P1：高优先级修复

- 引用与答案不一致；
- 应进入“不懂就问校长”但没有创建审核工单；
- 教练处理结果没有回传学员；
- OCR识别错误后仍高置信度匹配题库；
- 地区、车型或规则版本不明却给出确定结论。

#### P2：普通体验问题

- 回答过长或表达不够易懂；
- 页面响应较慢但仍可完成；
- 易错点或推荐题相关性一般；
- 提醒出现时机不理想。

### 16.2 进入真实学员试点的条件

```text
完成300—500条评测样本
→ P0问题为0
→ 标准题全链路正确率达到98%
→ 开放问答人工评审正确率达到90%
→ “不懂就问校长”异常处理链路验证通过
→ 数据隔离和删除流程验证通过
→ 进入30—50名真实学员试点
```

### 16.3 已确认的数据保留与隐私规则

- Dify与业务数据优先部署在国内云环境；
- 题目原始图片识别完成后短期保存，默认7天后删除；
- 对话、机器评测和人工审核记录默认保存180天，用于质量回溯；
- 可识别个人的学习记忆保存至试点结束后30天，之后删除或匿名化；
- 身份证、财务、缴费等敏感信息不进入Prompt与RAG知识库；
- 学员进入服务前查看必要的数据使用说明；
- 学员可申请删除个人问答与学习记忆；
- 法规或合同对数据保存提出更严格要求时，以更严格规则为准。

### 16.4 部署边界

- MVP优先在国内云环境自托管Dify；
- 业务数据库和图片对象存储独立于Dify；
- 模型API密钥由业务后端统一管理，不下发前端；
- 服务器规格、容灾和具体云厂商进入技术方案，不在PRD中硬编码。
