## 2. 产品到技术的适配判断

V2.0 是教育 Agent，不是自由规划型通用 Agent。其核心风险是错误识别、错误证据、错误结论和不可恢复，而不是任务规划能力不足。

因此采用：

- 固定业务 Workflow 承载 OCR 确认和标准题处理；
- 后端代码控制状态、权限、幂等、审计和标准答案；
- 模型只执行 OCR、解释和受约束推理；
- 无证据、证据冲突、低置信和失败场景显式降级；
- 不引入多 Agent、MCP、通用规划器和复杂微服务。

本阶段目标不是一次实现全部 Harness，而是先完成最小可验证的 2B 纵向切片：

图片提交 → 安全存储 → OCR 异步任务 → 低置信字段确认 → 标准题/现有问答链路 → 正式结果或降级 → 刷新恢复与审计。

## 3. Harness 适配

| Harness 要素 | V2.0 第一阶段实现 | 暂缓内容 |
|---|---|---|
| 工具 | upload_question_image、extract_question_ocr、confirm_ocr_fields、match_standard_question | 知识发布、完整评测运行 |
| 知识 | 现有标准题结构、OCR Schema、题目字段规则 | 正式供应商知识库扩充 |
| 观察 | assetId、ocrTaskId、requestId、状态、耗时、错误码、修正记录 | 完整成本和运营仪表 |
| 行动接口 | 上传、创建任务、查询、确认并创建问题 | 校长后台写操作 |
| 权限 | 学员只能访问本人图片、OCR 和问题 | 完整教练/审核员角色 |

## 4. 架构适配

继续使用模块化单体，不拆微服务。

    学员浏览器
       ↓ 同源请求
    Next.js BFF
       ↓ Cookie 换取后端身份
    FastAPI API
       ├─ 图片安全校验
       ├─ Asset/OCR 任务状态机
       ├─ OCR Provider Adapter
       ├─ OCR 字段确认
       ├─ 标准题匹配
       └─ 现有 Question/Answer 流程
       ↓
    SQLite + 开发期私有文件目录
       ↓
    阿里云百炼 qwen-vl-ocr

试点部署时，SQLite 和本地文件分别迁移到 PostgreSQL 与私有对象存储。业务层通过 Repository/Storage Adapter 隔离实现，避免页面或 API 直接依赖本地路径。

## 5. 技术栈结论

| 领域 | 采用方案 | 适配理由 |
|---|---|---|
| 前端 | 现有 Next.js 16.3.3、React 19、TypeScript strict | 不升级大版本，降低回归 |
| UI | 现有语义 CSS 与 Loom Token | 不在 OCR 阶段引入样式迁移 |
| 服务端状态 | TanStack Query + URL 标识 + 后端事实 | 支持刷新恢复和任务轮询 |
| 表单 | 原生表单；OCR 校正复杂后再评估 RHF | 首阶段字段有限，避免无必要依赖 |
| API 校验 | Zod | 延续 2A 运行时校验 |
| 后端 | FastAPI + Pydantic + SQLAlchemy + Alembic | 与现有代码一致 |
| 本地数据库 | SQLite | 支持开发与自动化测试 |
| 试点数据库 | PostgreSQL | 真实并发、备份和运维更适合 |
| 文件 | Storage Adapter；开发私有目录，试点对象存储 | 满足私有访问和删除策略 |
| OCR | qwen-vl-ocr，经百炼兼容接口调用 | 已完成真实能力验证 |
| 异步任务 | 持久化任务表 + 独立 Worker | 浏览器断开不影响任务，重启可恢复 |
| 测试 | pytest、Vitest、RTL/MSW、Playwright | 覆盖契约、恢复和真实浏览器 |

### 5.1 不新增的技术

- 不新增 Dify 依赖来承载 OCR 状态；
- 不新增 Chroma、RAGFlow 或另一套向量库；
- 不引入 Celery/Redis，除非持久化任务表无法满足真实负载；
- 不引入 Zustand；
- 不引入 Tailwind 或完整 UI 组件库；
- 不引入多 Agent、MCP、Scheduler 和通用任务平台。

## 6. 模型适配

### 6.1 OCR 主模型

- 主模型：qwen-vl-ocr；
- 调用位置：仅后端 Provider Adapter；
- 密钥：只从后端环境读取；
- 输出：必须经 Pydantic Schema 校验和字段归一化；
- 原始供应商响应：仅在受控调试/审计字段保存，不能直接下发前端；
- 超时和限流：有限重试，超过阈值进入 FAILED，可重新提交；
- 低置信字段：必须进入 WAITING_USER，不可直接创建正式问题。

### 6.2 文本模型

本阶段不改变现有回答模型路由。qwen3.7-plus、qwen3.6-flash 和 DeepSeek 只保留为后续受评测配置，不因 OCR 切片擅自调整正式答案策略。

### 6.3 标准答案约束

OCR 只负责读取题目，不负责决定答案。确认后的题干与选项进入标准题匹配；命中后，标准答案仍由题库确定，模型不得覆盖。

## 8. 状态机

OCR 后端状态：

    CREATED → QUEUED → PROCESSING
       → WAITING_USER → CONFIRMED → QUESTION_CREATED
       → FAILED
       → EXPIRED

规则：

- QUEUED/PROCESSING 可由 Worker 恢复；
- WAITING_USER 只能由学员确认；
- CONFIRMED 后重复请求返回同一 Question；
- FAILED 可有限重试，但不能覆盖历史错误；
- EXPIRED 后原图不可继续访问；
- 未知状态在前端映射为 stale 并重新查询，不作为成功。

## 9. API 适配

第一阶段候选契约：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/v1/assets/images | 上传并安全校验图片 |
| POST | /api/v1/ocr-tasks | 创建 OCR 任务，要求 Idempotency-Key |
| GET | /api/v1/ocr-tasks/{id} | 查询任务和可见字段 |
| PATCH | /api/v1/ocr-tasks/{id}/fields | 修正低置信字段 |
| POST | /api/v1/ocr-tasks/{id}/confirm | 确认并幂等创建问题 |
| GET | /api/v1/questions/{id} | 复用现有问题恢复接口 |

统一要求：

- 响应包含 requestId 和明确状态；
- 错误采用稳定 code 和安全 message；
- 所有资源执行 student_id 所有权校验；
- BFF 不缓存私有图片和 OCR 结果；
- 图片接口限制请求体、超时和并发；
- OpenAPI Schema 在编码前冻结。

## 10. 图片安全与隐私

- 支持 JPEG、PNG、WebP；每次一张；10MB 为待验证默认值；
- 同时检查扩展名、声明 MIME、文件头和可解码性；
- 拒绝 SVG、可执行文件、路径穿越和异常超大像素；
- 服务端生成随机 storage_key；
- 文件默认私有，前端只获得短期受权访问；
- 原图默认 7 天删除，删除行为必须可验证和审计；
- 日志不记录原图、base64、密钥和完整 OCR 原文；
- 身份证、财务、缴费图片不进入模型，应提示用户重新提交题目区域；
- 供应商数据保留与训练策略必须在真实试点前核验。

## 11. 可观测性

每个 OCR 链路记录：

- requestId、studentId 的不可逆标识、assetId、ocrTaskId、questionId；
- provider、modelId、schemaVersion；
- 排队、处理和总耗时；
- 重试次数、错误码、恢复次数；
- 字段数、低置信字段数、人工修正数；
- 输入图片类型和大小区间，不记录原始内容；
- 后续标准题是否命中和最终闭环状态。

第一阶段至少可计算：

- 上传成功率；
- OCR 任务成功率；
- 低置信确认率；
- OCR 修正率；
- 刷新恢复成功率；
- OCR 到正式问题转化率；
- 单图调用耗时和费用。

### 自动化

- 后端：文件伪装、超限、越权、幂等、状态迁移、重试、确认、删除；

- 记录原始识别、人工校正、模型耗时和成本；
- mock 通过不得替代 qwen-vl-ocr 真实冒烟；
- 真实 Key 只在本地/部署环境使用，不写入文档和测试快照。

## 13. 与 V2.0 PRD 的偏离

| PRD 能力 | 本阶段处理 |
|---|---|
| 完整 Harness | 只落 OCR 闭环所需最小集合 |
| 校长完整工作台 | 推迟到 2C |
| 知识审核与评测门禁 | 推迟到 2D |

| PostgreSQL | 本地继续 SQLite，试点前迁移 |
| Dify 选型 | 不在本阶段决策 |

这些属于按 PRD 切片实施，不改变产品目标。

## 15. 技术结论

- 当前架构可以增量承载 V2.0 第一阶段，无需重写；
- 第一阶段定义为 2B OCR 闭环；
- 使用持久化任务和固定 Workflow，不使用自由规划 Agent；
- qwen-vl-ocr 只负责识别，标准答案仍由确定性题库控制；
- 本地先用 SQLite 和私有目录，试点前迁移 PostgreSQL 和对象存储；
- 未确认项保持待确认，不写成正式业务规则；
- 本文评审通过前，不开始开发。
