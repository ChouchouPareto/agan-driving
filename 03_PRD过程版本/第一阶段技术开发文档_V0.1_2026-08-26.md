# 第一阶段技术开发文档 V0.1｜科目一可信问答最小纵向切片

> 状态：开发前技术评审稿  
> 日期：2026-08-26  
> 配套文档：当前项目PRD、`技术适配声明_V0.1_2026-08-26.md`、《AI Agent 产品 Vibe Coding 通用技术栈手册 V2.1》  
> 本文定义第一阶段如何实施和验收，不代表已经启动开发。

## 一、阶段目标

验证学员能否通过最小Web入口提出科目一文字问题，获得正确、易懂、带依据的回答；当仍不理解或系统无法可靠回答时，能否生成第二种解释或进入可追踪的校长工单。

### 本阶段交付

- 邀请码进入及最小数据说明；
- 科目一文字提问；
- 回答加载和流式状态；
- 直接答案、解释、易错点和依据；
- “已解决 / 还不懂 / 答案有问题”；
- 第二种解释；
- 创建并查询“不懂就问校长”工单；
- 问题、回答、依据、反馈和工单持久化；
- 标准题确定性匹配；
- Dify RAG与模型调用；
- 结构、证据一致性和风险检查；
- mock测试和真实模型冒烟；
- README启动与验收说明。

### 明确不做

- 图片、相机、OCR和对象存储；
- 完整学习记录、薄弱点和提醒；
- 完整教练/运营后台；
- 排班和SLA自动告警；
- 驾校效果看板；
- 完整题库运营后台；
- 多驾校复杂租户；
- ERP/SaaS、小程序和生产部署；
- 科目二、科目三、科目四；
- 多Agent和动态工具规划。

## 二、核心链路

```text
邀请码进入
→ 建立匿名会话
→ 输入科目一文字问题
→ 保存问题并生成request_id
→ 判断标准题候选或开放问题
→ 标准题查确定性题库；开放问题走Dify RAG
→ 模型基于标准答案或证据生成解释
→ 后端完成结构、依据和风险检查
→ SSE展示并保存正式回答
→ 学员反馈
→ 已解决：结束
→ 还不懂：第二种解释
→ 再次不懂/答案有问题：创建校长工单
→ 刷新后恢复回答和工单状态
```

## 七、状态机

### 问题状态

```text
SUBMITTED → ROUTING → RETRIEVING → GENERATING → VALIDATING → ANSWERED

异常：NEED_CLARIFICATION / NEEDS_REVIEW / REFUSED / FAILED
```

只有通过结构和质量检查的完整内容才能进入`ANSWERED`。流式残缺内容不能保存为正式答案。

### 工单状态

```text
SUBMITTED → QUEUED → PROCESSING → REPLIED → CLOSED
```

学员文案：

```text
提交给校长 → 校长在摸鱼 → 校长处理中 → 校长已回复 → 校长说好了
```

第一阶段实现创建、排队和查询；其余状态用受控测试数据验证，不开发完整教练后台。“校长在摸鱼”同时展示正式的2小时响应说明。

## 八、API

统一错误：

```json
{"error":{"code":"ERROR_CODE","message":"用户可理解的信息"}}
```

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/auth/invitations/verify` | 验证邀请码 |
| `GET` | `/api/v1/me` | 当前匿名学员 |
| `POST` | `/api/v1/conversations` | 创建会话 |
| `GET` | `/api/v1/conversations/{id}` | 恢复会话 |
| `POST` | `/api/v1/questions` | 提交问题 |
| `GET` | `/api/v1/questions/{id}/stream` | SSE回答流 |
| `POST` | `/api/v1/answers/{id}/feedback` | 学员反馈 |
| `POST` | `/api/v1/answers/{id}/explain-again` | 第二种解释 |
| `POST` | `/api/v1/review-tickets` | 创建工单 |
| `GET` | `/api/v1/review-tickets/{id}` | 查询工单 |
| `GET` | `/api/v1/health` | 健康检查 |

SSE事件：`status`、`chunk`、`done`、`error`。每次流必须以且只能以一个`done`或`error`结束。`chunk`不是正式答案。

## 九、AI工作流与Prompt

```text
标准题精确命中
→ 后端锁定标准答案
→ 模型只生成解释

未精确命中
→ 分类与改写
→ RAG检索与重排
→ 基于证据生成
→ 一致性与风险检查
→ 回答 / 拒答 / 转人工
```

第一阶段Prompt：

- `question_router`；
- `standard_explainer`；
- `rag_answerer`；
- `explain_again`；
- `quality_reviewer`；
- `refusal`。

Prompt必须独立版本管理，包含正确与禁止示例；输出经确定性解析和Pydantic校验；校验失败有限重试，仍失败返回统一错误或转人工。

## 十、最小页面

1. 邀请进入页；
2. 问一问页；
3. 回答、依据和反馈区；
4. 校长工单状态页。

必须覆盖邀请码错误、空状态、路由/检索/生成/检查、回答完成、无依据、二次解释、工单排队、网络中断、模型超时和刷新恢复。

UI以`Loom参考UI统一设计系统_v1.0.md`为有效依据：主色`#625DF5`，中性浅色、细边框、紧凑圆角；不用儿童化、Comic、Claymorphism和橙色CTA；不向学员展示置信度百分比。

## 十一、第一阶段知识样本

建议准备：

- 50道人工确认的标准题；
- 10–20张法规或教学知识卡片；
- 30条独立测试样本，覆盖标准题、口语化、歧义、无答案、范围外和来源冲突。

这是第一阶段临时工程样本，不修改PRD的真实试点门槛。正式试点前仍需不少于500题、50–100张知识卡和300–500条评测样本。

## 十二、测试

### mock测试

- 邀请码有效、无效、过期；
- 学员数据权限；
- 标准题精确命中和低阈值拒绝；
- 模型不得改变标准答案；
- RAG有依据、无依据和来源冲突；
- 模型格式错误、超时、限流、错误Key和SDK初始化失败；
- SSE以`done/error`结束；
- 三种学员反馈；
- 第二解释和工单创建；
- 服务重启后状态恢复；
- 日志不含Key和敏感原文。

### 真实模型冒烟

使用真实Key验证标准题、开放RAG、无依据拒答、第二解释和模型失败。记录模型、Workflow、Prompt版本、首字时间、总耗时、Token、成本、首测格式、重试和人工评价。

## 十三、验收标准

### 功能

- [ ] 邀请码进入可用；
- [ ] 可以提交文字问题；
- [ ] 标准答案来自题库；
- [ ] 开放问题展示依据；
- [ ] 无依据时不编造；
- [ ] 三种反馈可用；
- [ ] 第二解释不改变事实；
- [ ] 异常可创建工单；
- [ ] 刷新不丢失正式回答和工单；
- [ ] 错误状态提供下一步。

### 工程

- [ ] API输入、输出和错误均有Schema；
- [ ] 数据库可通过迁移初始化；
- [ ] Prompt和模型配置未硬编码；
- [ ] Key未进入前端、仓库和日志；
- [ ] 状态机可恢复；
- [ ] SSE正确收尾；
- [ ] mock测试通过；
- [ ] 真实模型冒烟完成并记录；
- [ ] README说明启动与验证；
- [ ] 没有用mock冒充真实验收。

以下任一情况视为P0，阶段不得通过：模型改错标准答案、无依据强答、学员异议后继续强化原答案、跨学员数据泄漏、残缺内容被保存为正式答案、mock结果冒充真实验证。

## 十四、产品验收操作

1. 使用有效和无效邀请码；
2. 提交一条标准题并核对答案；
3. 展开依据；
4. 提交开放理论问题；
5. 点击“还不懂”查看第二解释；
6. 再次表示不懂，确认创建工单；
7. 对另一个答案点击“答案有问题”；
8. 刷新并确认回答和工单仍存在；
9. 模拟网络或模型失败；
10. 查看真实模型冒烟记录。

## 十五、启动开发前确认

1. 使用哪个Dify环境；
2. 是否已有模型Key；
3. 第一阶段模型测试预算；
4. 谁审核第一批50道题和10–20张知识卡；
5. 确认第一阶段暂不开发OCR、完整后台、提醒和看板。

没有真实Key不阻塞mock开发，但阻塞真实模型验收。
